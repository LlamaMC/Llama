# Architecture decisions

This file records the design decisions for the runtime. Each decision names what was chosen and why. The status column
says what the code does today. Where the code lags a decision, the status says so, and the decision still holds.

## Thread model

```
Netty / Network ─┐
                 ├─► Tick owner (state changes, lifecycle, commit)
Plugins / API ───┘          │
                  ┌─────────┴─────────┐
              CPU workers         IO workers
        (generation, math)   (snapshots, persistence)
```

- The tick thread owns all loaded world state, player state and plugin callbacks that touch them.
- Netty threads and plugin threads never mutate loaded state. They hand work to the tick thread through the scheduler.
- CPU workers compute on their own buffers and return immutable results. They never change a loaded chunk.
- IO workers write immutable snapshots. They never read or change loaded state.
- No blocking disk or network call runs on the tick thread.

## 1. Players and networking

Decision: a complete, state-based player lifecycle. Registration does not depend on the chat implementation.

- Connection states HANDSHAKE, LOGIN, CONFIGURATION and PLAY are traversed in order. Each transition is checked.
- A player is registered only after authentication, after the configuration state has finished, and after the world
  join packets are ready. Registration runs on the tick thread.
- `PlayerRegistry` is keyed by UUID and holds the connection. A second login with a UUID that is already online
  disconnects the old session, as vanilla does.
- Events: `PlayerPreJoinEvent` (cancelable, carries a denial reason), `PlayerJoinEvent`, `PlayerQuitEvent`.
- Quit runs exactly once per player. It is triggered by a disconnect packet and also by an unexpected socket close.
- Outbound disconnect packets use the verified 26.3 IDs: login_disconnect 0, configuration disconnect 2, play
  disconnect 32. Source: the official 26.3 `reports/packets.json`, generated by the official server.
- Chat: every server-generated and every player-chat message is sent as `system_chat` (124). Player chat from the
  serverbound `chat` packet (9) goes through `ChatEvent` and is re-broadcast as system chat. The runtime does not
  verify or forward chat signatures, so the server never sends signed `player_chat` (66). Signatures are read and
  ignored. The client shows the messages as system messages.
- Commands: serverbound `chat_command` (7) and `chat_command_signed` (8) dispatch to the command registry with the
  player as the sender.
- Status: the packet IDs above are verified. Implementation status is tracked in section 10.

## 2. World writes and persistence

Decision: single writer, asynchronous persistence, and crash-consistent region storage.

- `setBlock` on a loaded chunk runs on the tick thread only and fails with `IllegalStateException` elsewhere.
- `setBlockAsync` queues the write on the tick thread through the scheduler and returns a future.
- Every mutation increments the chunk's revision and marks the chunk dirty.
- Saving takes an immutable snapshot on the tick thread and hands it to an IO worker. After a successful save the
  dirty flag is cleared only if the revision is still the snapshot's revision. Otherwise the chunk stays dirty.
- Autosave runs every 30 seconds and coalesces repeated changes to the same chunk into one write.
- Storage uses copy-on-write data areas and two alternating index slots, each with a generation number and a checksum.
  A commit writes the new index into the older slot. A reader takes the valid slot with the higher generation. A crash
  during a commit leaves the previous slot intact, so the region stays readable.
- Persistent identity of a block state is its string form (`namespace:key[properties]`), not its runtime registry ID.
- Status: section 10. The current storage is the Vicuna format. Its chunk payload stores each palette entry as the
  state string, so properties are kept. Data version 5024 uses one-byte indexes for up to 256 states, and 5025 uses
  two-byte indexes above that. Data version 5023, which stored the key and the properties separately, is still read.

## 3. Command senders and permissions

Decision: one sender model, one permission service, one central check.

```java
public interface ICommandSender {
    String name();
    boolean hasPermission(String permission);
    void sendMessage(Component message);
}
```

- `ConsoleSender` has every permission.
- `PlayerSender` is built from `IPlayer`. Its permissions come from `permissions.toml`, looked up by UUID.
- Permission nodes are namespaced. Commands use `llama.command.<label>` unless `@Command.permission` names another node.
  Core nodes use `llama.`, and plugins register their own nodes through the permission service.
- `PermissionDefault` has `TRUE`, `FALSE` and `OP`. `OP` grants the node to senders that hold `llama.op`. The console
  holds `llama.op`.
- Resolution order: an explicit grant for the user, then a grant through one of the user's groups, then the node's
  default. Groups are read from the config. No rank system beyond that.
- `CommandRegistry.dispatch(sender, line)` checks the permission before it runs anything.

## 4. Plugins

Decision: an own modular loader with explicit constructor injection. No DI framework and no classpath scanning.

- Metadata lives in `llama-plugin.json`: `id`, `name`, `version`, `main`, `depends`, `softDepends`.
- Plugins are loaded from the `plugins/` directory, one jar each. Each jar gets its own class loader. The parent is the
  server class loader, so the plugin shares the API classes and cannot replace them.
- Dependencies are resolved before anything loads, as a graph with a topological sort. A cycle disables every plugin
  in it. A missing hard dependency disables the plugin that needs it. A missing soft dependency only changes the order.
- Lifecycle: LOAD (constructor injection) → ENABLE → DISABLE. DISABLE runs in reverse order.
- Injectable types: `IScheduler`, `IEventBus`, `ICommandRegistry`, `IPermissionService`, `ILlama`, `IPluginContext`
  and `org.slf4j.Logger`. A constructor parameter of any other type fails that plugin with a message naming the type.
- A plugin can publish a service through `IPluginContext.provide`. A plugin that declares a hard dependency on that
  plugin receives the service through its constructor.
- A failing plugin is disabled and logged. It does not stop the server start.
- No hot reload in this version.
- Status: section 10.

## 5. Chunk eviction

Decision: tickets plus an idle timeout, with incremental scanning.

- Tickets keep a chunk loaded. There are four kinds: player, plugin, generation and system.
- A chunk with no tickets becomes an eviction candidate after 90 seconds without access. Under memory pressure the
  timeout is reduced to 30 seconds. Pressure means used heap above 85 percent of the maximum.
- The candidate scan runs inside the tick, with a fixed budget of chunks per tick, so the cost per tick is bounded.
- Lifecycle: LOADED → EVICTING → UNLOADED. A new ticket during EVICTING cancels the eviction.
- A dirty chunk is saved before it leaves memory. Nothing is unloaded during generation or an active save.
- A failed save keeps the chunk loaded and records a diagnostic.
- Status: section 10.

## 6. Block-state palettes above 256 states

Decision: three palette modes with automatic promotion.

| Mode     | Condition   | Storage                                            |
|----------|-------------|----------------------------------------------------|
| Single   | 1 state     | One state, no packing                              |
| Indirect | 2 to 256    | Local palette, bit-packed indexes, 4 to 8 bits     |
| Direct   | 257 and up  | Global state IDs, bit-packed to the registry width |

- The direct width is the bit width needed for the global block-state registry (for example 16 bits for the 35,723
  states of the official 26.3 registry), not a fixed width.
- Promotion happens when a section passes 256 distinct states. Demotion does not happen on each update. It happens
  during compaction on save, to avoid switching modes repeatedly.
- The in-memory representation is separate from the protocol encoder. The protocol encoder picks the mode for the
  wire format.
- The global registry comes from the official 26.3 `reports/blocks.json`, generated by the official server.
- Status: section 10.

## 7. Shutdown

Decision: one global deadline of 60 seconds. No pool waits a fixed time on its own.

| Window   | Stage                                                                        |
|----------|------------------------------------------------------------------------------|
| 0 to 5 s | Stop accepting connections. Disconnect players. Fire quit events.            |
| 5 to 15 s| Disable plugins and stop their tasks. Freeze world state.                     |
| 15 to 50 s| Flush and persist chunks, players and world data.                            |
| 50 to 60 s| Terminate executors, Netty and remaining resources.                          |

Shutdown disconnects players first, then flushes dirty chunks before the storage closes.

- The windows are budgets. A stage that finishes early hands over to the next stage at once.
- Each stage waits for `min(its budget, time left until the deadline)`, using `System.nanoTime()`.
- At the deadline the runtime halts with a diagnostic dump. A shutdown counts as clean only when every required write
  has completed.
- Status: section 10.

## 8. Blocking, futures and deadlocks

Decision: no blocking future waits on the tick thread or on worker threads.

- World generation is an asynchronous dependency pipeline. Workers return results as `CompletionStage`s. Dependencies
  use `thenCompose` and `thenCombine`, and results are applied on the tick thread through the scheduler.
- Every asynchronous step names its executor. Nothing runs on the common pool by accident. The only `Runnable::run`
  stages are in `LlamaPromise.thenApply` and `thenCompose`, and each carries a comment saying why.
- Llama's own blocking chunk methods (`chunkNow`) throw on the tick thread and on world worker threads. This is in
  place today.
- `join()` on an arbitrary Java future cannot be intercepted, so it is covered by static rules (see the Pureline
  profile) and by the watchdog, which dumps the stacks of a hung tick.
- Blocking waits are allowed only in bootstrap code and in tests, and only with a timeout.

## 9. Technical debt

- `StreamCodec` loses its `Objects.requireNonNull` calls and gets explicit guard clauses with specific exceptions.
- Command handlers can be method-annotated. `CommandRegistry.register(owner, handler)` scans the public methods of an
  explicitly registered handler instance. The owner is the plugin, or the runtime itself. Method signatures are
  checked at registration. An invalid handler fails with a message that names the method and the reason.
- Classpath scanning does not happen anywhere.

## 10. Implementation status

Filled in as work lands. Each line says what is in the code, with the commit that added it.

- **1. Players and networking** (2980bb8, dfeb03d, 0d8dd4f, 484e102, cd17aef): players are registered on the tick thread
  after the configuration acknowledgement and once the join packets are ready. The registry is keyed by UUID, a second
  login kicks the old session, and the pre-join, join and quit events fire. A login admitted after shutdown begins is
  refused with "Server closed" before any pre-join event. Disconnect and chat/command packet IDs are verified against
  the official 26.3 report. Not done: there is no authentication. The UUID is an offline UUID derived from the user
  name, and `online-mode` is read but unused.
- **2. World writes and persistence** (1bc9c94, 8dbf36e, 967deb5, 9a7037b): `setBlock` runs on the tick thread only, and
  `setBlockAsync` queues it there. A write bumps the chunk's revision and marks it dirty. Autosave starts a save of each
  dirty chunk every 600 ticks (30 s) and skips a chunk whose save is still running. A save clears the dirty flag only if
  its revision is still current. Snapshots are copy-on-write per revision, and each is taken under the chunk's monitor
  on the thread that starts the save. The Vicuna region file appends each chunk payload, writes the new directory into
  the inactive copy, and commits it into the alternating slot, so a reader takes the valid commit with the higher
  generation. Checksums are CRC32C. Data version 5024 stores state strings with one-byte indexes, 5025 uses two-byte
  indexes above 256 states, and 5023 is still read. Compaction reclaims replaced chunk payloads
  once their dead bytes exceed half of a region file of at least 1 MiB.
- **3. Command senders and permissions** (7b7752c, 0ea4f61, 75964a7): `ConsoleSender` grants every permission.
  `PlayerSender` checks the player's grants by UUID. Commands use `llama.command.<label>` unless `@Command.permission`
  names another node, and `CommandRegistry.dispatch` checks the node before it runs the command. A user's permission is
  resolved in this order: an explicit grant for the user, a grant through one of the user's groups, then the node's
  default (`TRUE`, `FALSE` or `OP`, which needs `llama.op`).
- **4. Plugins** (557f619, 1ba79fb, 599d643, 0a8410d): `PluginLoader` loads the jars in `plugins/` in dependency order,
  using Kahn's algorithm over `depends` and `softDepends`. Each jar has its own class loader, whose parent is the server
  loader. A cycle disables every plugin on it, and a missing hard dependency disables the plugins that need it.
  Constructor injection supplies `IScheduler`, `IPermissionService`, `IEventBus`, `ICommandRegistry`, `ILlama`, `IPluginContext`
  and `Logger`, plus the services that a hard dependency publishes through `IPluginContext.provide`. `disable()` runs in
  reverse load order, and the plugin's handlers and commands are removed after it. Not done: there is no hot reload.
- **5. Chunk eviction** (141514a, 80813d5, 49f6200, f4e0808): tickets (`PLAYER`, `PLUGIN`, `GENERATION`, `SYSTEM`) keep a
  chunk loaded. A loaded chunk with no tickets is evicted after 1800 ticks (90 s) without access, or after 600 ticks
  (30 s) while used heap is above 85 percent of the maximum. Each tick examines at most 64 chunks. A dirty chunk is saved
  before it leaves memory, and its removal waits for any running save. A failed save keeps the chunk loaded, logs a
  warning and starts a new idle period. A new ticket or any access during `EVICTING` cancels the eviction. `unloadChunk`
  uses the same path.
- **6. Block-state palettes** (d0f94d6, 568ea0b, 4949e53, 7b7f73d): the protocol encoder picks the mode for each section
  from its count of distinct states: single for one state, indirect for 2 to 256 states (4 to 8 bits), and direct above
  256, where entries are global state IDs packed at the bit width of the registry. The global registry is read from
  `minecraft/26.3/blocks.tsv`, which `scripts/generate_block_states.py` writes from the official `blocks.json`. Not done:
  direct palettes exist only in the protocol encoder. In memory, a chunk keeps one palette with 16-bit indexes, so there
  is no promotion, demotion or compaction on save.
- **7. Shutdown** (e858ff1, 2556101, 414d9cb, 1f95868, 0329f02, 9a7037b, 8834d69): the shutdown sequence in `Llama`
  disconnects players, closes the console, stops the watchdog, disables plugins, stops the tick loop, closes the
  scheduler and the server, and closes the worlds, in that order. Each stage waits for its own budget (players 5 s, tick
  loop 10 s or 1 s when hung, watchdog 1 s, server 5 s, worlds 35 s), capped by the time left before one 60-second
  deadline. World close saves the dirty chunks before it closes storage. Shutdown is reported clean only when every stage
  finishes, and the JVM halts with a thread dump at the deadline. Not done: the fixed windows of the decision table
  (0 to 5 s, 5 to 15 s, 15 to 50 s and 50 to 60 s) are not used.
- **8. Blocking, futures and deadlocks** (1518ff7, 44d94ea, 89213bc, b1fa1f1): `chunkNow` throws on the tick thread and on
  world worker threads. Chunk loads chain `supplyAsync` steps with `thenCompose`: load on the storage pool, generate on
  the generation pool, then write on the storage pool. Every `CompletableFuture` async call names its executor.
  `TickScheduler.supplyAsync` runs its task on a virtual thread. The watchdog dumps the stacks of a hung tick. Not done:
  `thenCombine` is not used, a load completes on the worker thread that finishes it rather than on the tick thread
  through the scheduler, and `join()` and `await()` are not checked on the tick thread (`docs/API.md` section 9).
